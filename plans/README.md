## Recommended execution order

All five plans are independent (no plan depends on another), so they can be done
in any order or in parallel worktrees. 004 and 005 both live in the Squiggle API
layer but touch disjoint files (004 explicitly does not touch
`squiggle.serverfns.ts`/`cache.ts`; 005 touches only those) — safe in parallel.
Suggested addition to the sequence below: do **005 before or alongside 004**
(it's small, and 004's live-score traffic makes per-instance cache inconsistency
more visible), and schedule 004's final verification for a game day (Thu–Sun
in-season) so the live e2e step can actually run. Original 001–003 sequence:

1. **003 (deps)** — fastest, fully mechanical, gets a green audit and confirms
   the toolchain still builds. Low risk warm-up.
2. **002 (scoring tests)** — pure refactor + tests, zero behavior change, gives
   the core scoring logic a safety net.
3. **001 (RLS lockdown)** — highest **severity** (a live security exposure), but
   MED risk and it has **manual operator steps** (add `SUPABASE_SERVICE_ROLE_KEY`
   to every environment, apply the SQL migration to the Supabase project). Do it
   when the operator is available to complete and verify those steps. If you want
   to stop the security bleeding first, this can equally go **first** — it does
   not depend on the others.

## Findings surfaced in the audit but NOT turned into plans

The audit found these; the operator chose not to plan them for now. Recorded so
they are not re-audited from scratch next run:

- **#4 Server-side caching of leaderboard/group-tips/compliance** (perf, S/M):
  ~~`tips.ts` re-fetches all Clerk users + all tips per request; the `withCache`
  utility already exists and is used for Squiggle but not here. Worth doing;
  depends on 002. Not selected this round.~~ **SUPERSEDED by plan 005**
  (2026-07-04): `withCache` is a per-instance in-memory Map — on Vercel
  serverless it is not shared across instances, so extending it is the wrong
  direction; 005 removes it entirely. The underlying perf concern (re-fetching
  all Clerk users/tips per request) remains real; the platform-correct fix is

  hygiene, S): `tips.repository.ts:28` and ~11 `console.*` sites log PII and
  config on every write. Low risk to fix. Not selected.

  TanStack.com template (wrong setup: says `pnpm`, documents a docs-site that
