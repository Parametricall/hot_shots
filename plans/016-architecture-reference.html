Topic 1 of 8

Opening a page

Pages draw from a cache in the browser first, then refresh it from your server. The server reads your tables, never Squiggle.

How it works

  1. Each page asks for data with a TanStack Query key that starts with the Season, like ["afl", "season", 2027, "games"]. Switching Seasons switches every query at once.
  2. Queries don't call the server directly. They ask the service registry for a service, such as squiggleService.getGames. The live site registers services that call server functions. The Demo registers its own (topic 8).
  3. A server function runs on Vercel. It checks the session cookie, then reads through squiggleDataRepository or a tips repository using the server-only secret key.
  4. The whole query cache is saved to localStorage for 24 hours, and cleared by each deploy. An installed app opens straight onto its last screen.
  5. Games count as stale after one minute. Live updates keep them current while the app is open. Reopening or refocusing the app refetches them from your database.

Topic 2 of 8

Signing in

Supabase Auth with Google or an emailed one-time code, and no passwords. Every step runs on your server, which sets the session cookie itself. JavaScript in the page can't read that cookie.

How it works

  1. Invite-only. The hook refuses any email address with no row in invitations, before Supabase creates an account.
  2. Cookies only the server touches. Your server sets the session as HttpOnly cookies in its responses. Safari caps cookies written by JavaScript at 7 days, but not these, so nobody has to sign in every week.
  3. The guard. Every route under _authenticated calls getSessionUserId() first, and sends anyone without a session to /sign-in. getClaims() also refreshes a session that's about to expire.
  4. Profile, Tipster, entry. A new account gets a Profile (name and photo). Opening AFL Tipping for the first time makes them a Tipster. Opening it during a Season enters them in that Season's Competition, and Auto-tips start from that moment.

Topic 3 of 8

Submitting a Tip

One server function decides whether a Tip may be saved and whether it's an Underdog tip, using your copy of the Game and the Model tip as they stand at that moment.

Rules it enforces

  • Lockout is the moment the Game starts. Until then a Tip can be changed and nobody else can see it. Group tips hides other people's teams until the start.
  • An Underdog tip is judged against the Model tip as it stood when the Tip was made. It stays an Underdog tip even if the Model changes its mind later.
  • The Margin is only kept for the Margin game, the first Game of the Round by start time.
  • Saving the same Game again replaces the earlier Tip, keyed on Game and Tipster.

Topic 4 of 8

Auto-tips & the Leaderboard

The Leaderboard is worked out fresh on each request from four inputs. Missed Games are filled with Auto-tips first, so everyone is scored on the same set of Games.

The rules

  • Auto-tip: a Tipster who hadn't tipped a Game by Lockout gets the Home team. It only applies to Games whose Lockout came after they entered the Competition, and it's never an Underdog tip.
  • Score is the number of Correct tips. In a Draw, every Tip on that Game is wrong.
  • Margin difference is how far a Margin was from the result. Tipping the wrong team adds the real margin to the tipped one. The lowest season total breaks ties.
  • Tipsters still level share the rank. A finished Season's last place is the Wooden spoon, unless the Competition has three or fewer.
  • The Underdog quota is two per Round outside Finals. Missing it is called out but doesn't cost points.

Where it lives

Why it's computed, not stored: Auto-tips and scores depend on Game results that change during a Round. Working them out per request from Tips and Games means there's nothing to get out of step (ADR 0001).

Topic 5 of 8

The Squiggle sync

A schedule, not visitors, decides when Squiggle is asked for data. Every 10 minutes Supabase calls your endpoint, and a planner works out whether anything is due.

What gets fetched, and when

Data When Per day
Fixture Hourly in-Season (Games not yet complete). A full reconcile daily. Daily off-Season. A finished Season: never again. ≤ 25
Next year's Fixture Daily, until Squiggle has Games for it 1
Model tips Hourly for Rounds with a Game in the next 7 days, otherwise daily ≤ 48
Ladder 10 minutes after a Game completes, plus a daily reconcile in-Season ≤ 10
Teams Weekly, or when a Game names a team you don't have (at most hourly) < 1

Guardrails

  • At most 10 requests a run and 300 a day. Past that, the planner plans nothing.
  • After a failure, that job waits 1, 2, 4 … up to 60 minutes.
  • A response that doesn't match its Zod schema writes nothing, so the last good data stays.
  • Live data rule: for a Game the live ingest updated in the last 10 minutes, the sync doesn't overwrite its scores. Squiggle's Standard API runs up to 60 seconds behind its Event API.
  • Every request carries a User-Agent with your contact email, from SQUIGGLE_CONTACT_EMAIL.

Topic 6 of 8

Live scores

One connection to Squiggle for the whole site, held in runs of about five minutes. A database trigger fans every change out to signed-in tabs over Supabase Realtime.

One run, step by step

  1. Takes the lease, a single database row that only one run can hold. If another run has it, this one stops straight away.
  2. Checks afl_games for a Game that's live or starts within 30 minutes. If there's none, it stops.
  3. Opens sse.squiggle.com.au/events, which covers every Game, with your User-Agent.
  4. Writes each event's live fields to afl_games. A Game that finishes without a winner gets one from the scores, and a Draw gets none.
  5. If the connection drops, it reconnects after 2, 4, 8, 16, then 30 seconds. A refusal such as a 403 stops the run.
  6. At about 290 seconds it closes, releases the lease, and records a live run.

In the browser

  • A tab joins the channel only while a Game is live or about to start, and leaves when the last one finishes.
  • It gets a short-lived access token from getRealtimeToken, never the refresh token, and refreshes it 5 minutes before it expires.
  • If the channel drops, it rejoins (2 s, doubling to 60 s), then refetches Games once in case it missed an update.
  • Fallback: setting VITE_LIVE_SCORES=relay brings back the old per-tab relay until Opening Round proves the new path.

Topic 7 of 8

Who can read what

The browser has the publishable key, which is public by design, and a session cookie. Neither can read a table. Everything goes through your server, except one Realtime channel.

The rules

  • Every table has row-level security on and no policies. A new table's migration must turn RLS on too.
  • The secret key is only ever on the server. No secret may have a VITE_ prefix, because Vite builds every VITE_* variable into the browser bundle.
  • The lease, cron and trigger functions have execute revoked from anon and authenticated. Without that, the public API could call them.
  • Realtime's "Allow public access" is off, so only private channels work. The one realtime.messages policy lets signed-in users receive on one topic. Nobody can send.
  • The sync endpoints compare the Bearer secret in constant time. A missing secret answers 503, a wrong one 401.

Topic 8 of 8

The Demo

The public Demo is the same site, built with VITE_DEMO=true. It runs entirely in the visitor's browser over a 2026 snapshot, with no Supabase, no Squiggle and no sign-in.

What that means for new code

  • New data has to reach components through the service registry, or the Demo won't have it.
  • A Demo-only import is gated with the condition written out (import.meta.env.VITE_DEMO === "true"), so the live build drops it.
  • The Demo keeps no query cache in the browser. Each visit starts fresh.
